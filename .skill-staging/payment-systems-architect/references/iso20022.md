# ISO 20022 Reference

## Use This Reference

Read this file when the task depends on ISO 20022 message semantics, canonical field design, message choreography, or migration from legacy payment formats.

## Core Framing

- Treat ISO 20022 as a rich business message standard, not merely an XML schema.
- Separate business intent, transport envelope, and local processing state.
- Preserve semantic meaning during mapping; do not reduce everything to a flat payment record unless the use case truly needs that simplification.

## Common Message Families

- `pain.*`: customer-to-bank initiation and status flows.
- `pacs.*`: FI-to-FI clearing and settlement instructions.
- `camt.*`: reporting, notifications, investigations, and cash management.
- `head.*` or business application headers: routing and business envelope context where applicable.

## Modeling Rules

- Keep identifiers separate: instruction ID, end-to-end ID, transaction ID, UETR or global tracker, message ID, and settlement reference all serve different purposes.
- Preserve party roles explicitly: debtor, creditor, initiating party, instructed agent, instructing agent, debtor agent, creditor agent, and ultimate parties.
- Model amount dimensions explicitly: instructed amount, interbank settlement amount, charges, settlement currency, and FX context.
- Preserve remittance structure when possible instead of flattening it into a free-text blob.
- Store original raw messages for evidence, replay, investigation, and mapping improvement.

## Canonical Model Guidance

Create a canonical model only when it reduces complexity across rails or channels. Keep these principles:

- Normalize shared business concepts, not every possible XML element.
- Keep a native extension area for scheme-specific or market-practice fields.
- Preserve enough detail to reconstruct outbound messages and audit business meaning.
- Record mapping provenance so operators can explain how a canonical field was derived.

## Message Choreography

Think in terms of choreography, not one-off requests:

- Initiation
- Validation and enrichment
- Acceptance or rejection
- Clearing submission
- Clearing response
- Settlement confirmation or position reporting
- Return, reject, reversal, cancel, and investigation flows

Always ask which messages establish obligation, which only acknowledge receipt, and which indicate settlement or finality.

## Migration Guidance

When modernizing from legacy formats or bespoke APIs:

- Map business concepts first, field formats second.
- Identify information loss early, especially around party data, remittance, charges, and status granularity.
- Avoid a temporary canonical model that bakes in legacy constraints as permanent design.
- Support coexistence if upstream and downstream participants migrate at different times.

## Review Checklist

- Are identifiers mapped without collapsing distinct references?
- Are party roles preserved accurately?
- Is finality differentiated from technical acknowledgement?
- Can returns, rejects, and investigations reference the original transaction cleanly?
- Is the canonical model minimal but semantically faithful?
- Are raw inbound and outbound payloads retained for audit?
